# difffocus

**九成是格式改动时，真实改动在哪。**

`difffocus` 把版本差异**按语义分类**再排序：新增、删除、重命名、
纯格式改动、逻辑改动分别成组，格式改动单独归到一处，
并且提供一个开关把它从主视图里收起来。

- 零依赖，Python 3.10+ 标准库即可运行
- 单文件，`difffocus.py` 拷走就能用
- **机械可判定的直接判；需要人判断的标出来，但不替你下结论**

## 安装

零依赖，Python 3.10+ 即可：

```bash
pip install henrytooth-difffocus
```

装完直接用命令名调用：

```bash
difffocus --help
```

也可以不用安装，直接把 `difffocus.py` 拷走用——它只依赖标准库。

## 为什么需要它

评审代码时最消耗精力的情形，是一份 diff 里大部分行数都在改缩进和换行。

真实的逻辑改动只有几行，却要翻到最后才看到。
如果 diff 有 400 行，其中 350 行是格式化工具干的，
逐行读就是浪费——但「不看」又怕漏掉。

`difffocus` 的做法是**先分类，再排序**：

```
变更总数：12
有效变更：4
格式噪音：8（占 66.7%）

  逻辑改动：2
  新增：1
  纯格式改动：8

【逻辑改动】2 条
  ? app.py @@ -1,8 +1,9 @@
      - def old_name():
      + def new_name():
      （需人判断）同一块内删增内容形态一致，可能是移动或重命名——需人工确认
```

拿到这个输出，你可以只读「有效变更」那一组，
或者干脆用 `--hide-format` 把噪音收起来。

## 用法

```bash
# 分析一个 diff 文件
python difffocus.py analyze --input diff.patch

# 把纯格式改动收起来，只看有效的
python difffocus.py analyze --input diff.patch --hide-format

# 机器可读输出
python difffocus.py analyze --input diff.patch --json

# 直接比较两个文件
python difffocus.py compare --old old.py --new new.py
```

## 五种分类

| 类型 | 判定方式 | 是不是结论 |
|---|---|---|
| **逻辑改动** | 同一块里内容相似的删增行，归一化后仍不同 | 是，机械可判定 |
| **纯格式改动** | 同一块里归一化后完全一致 | 是，机械可判定 |
| **新增** | 没有配对上的新增行 | 是，机械可判定 |
| **删除** | 没有配对上的删除行 | 是，机械可判定 |
| **重命名** | 同一块里删增行的词法结构一致 | **否**，需人工确认 |

**「纯格式改动」的判定是保守的**：只有归一化之后**完全一样**才算。
归一化会去掉首尾空白、把连续空白压成一个空格、把双引号与中文引号统一成单引号。
任何其他差异都归为逻辑改动——宁可多报，不要漏报。

**「重命名」永远标记为「需人判断」**。
文本上，「把 `old_name` 改名为 `new_name`」和
「把 `old_name` 这个变量改成 `new_name`」是完全一样的。
工具能看出形态一致，但判断不了意图。

这一点在输出里用 `?` 标记，并附上说明：

```
  ? app.py @@ -1,8 +1,9 @@
      （需人判断）同一块内删增内容形态一致，可能是移动或重命名——需人工确认
```

## 已知局限

- **只处理 unified diff**。不解析 git 的二进制 diff、rename/rename 头部、
  mode 变更、子模块变更，也不处理 diff 里的 hunk 元信息。
- **重命名识别能力有限**。只靠 diff 文本里的词法形态，
  不读 git 历史，因此**跨文件的移动**（文件改名、内容不变）识别不出来。
- **不看提交信息**。作者写 `renamed foo to bar` 对工具没有帮助。
- **格式改动只覆盖三类**：缩进/空白、引号风格、行尾空白。
  换行符统一、导入排序、注释增删**不算**格式改动——虽然它们常被误认为噪音。
- **不判断改动的重要性**。它说「这是逻辑改动」，不说「这个改动重要」。
- **不做语义分析**。不区分「修 bug」和「加功能」。
- **不折叠长行**。不提供 `--ignore-all-space` 之类的选项。
- **不处理 CRLF 与 LF 的差异**。行尾差异在这套归一化里**不**算格式改动
  （因为归一化只 strip 首尾空白，不动行内的 `\r`），
  这类差异通常出现在整个文件被重写的场景里。
- **配对基于文本相似度**，阈值固定为 0.5，不随语言调整。
- **不做统计分析**。不给「本次变更的噪音占比趋势」这类跨次比较。

## 为什么还要做这个

`git diff --stat` 告诉你「改了 400 行」，但没告诉你**哪几行值得看**。

`difffocus` 的价值在于那个切换成本：把噪音归类之后，
你从「翻 400 行」变成「读 4 行」。
它不替你判断什么重要，只是**把噪音挪到不挡路的地方**。
